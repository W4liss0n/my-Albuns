# UI acceptance artifact hashing

The project does not currently hash screenshots, fonts or other captured UI-acceptance artifacts as part of the commit-bound review manifest.

## Why this is out of scope

The acceptance evidence is currently an internal, local review aid. The runner records the source commit and dirty state, capture and human review remain separate states, and the product gates validate the scenario manifest and rendered output. Hashing every generated byte would harden the evidence against replacement after capture, but it would not validate another product behaviour or make an unreachable UI path reachable.

Making those hashes authoritative would also require defining artifact retention, canonical font and browser inputs, cross-host reproducibility and the trust boundary for the reviewer. That is evidence-provenance infrastructure rather than a correction to the current UI or a refactor of its production architecture.

The review policy still requires scenarios to describe honestly whether they use production ports, fixtures or fake adapters. Missing critical visual states remain actionable regardless of this decision.

## Reconsider when

Reconsider hashing when UI evidence is published outside the worktree, retained as a release artifact, compared across hosts in CI, used for approval across a trust boundary or consumed as an auditable release gate.
